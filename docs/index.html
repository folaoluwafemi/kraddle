KRADDLE FORMAT / OVERVIEW

Alpha specification

Keep software connected to what it means.

The Kraddle Format is a project-native, database-free structure for recording what software does, what it is for, what it must preserve, and how every part relates.

i
Early specification

The semantic model is the focus. Byte-level assignments may change before the first implementation.

04EvidenceWhat became true

Why it exists

Software meaning is usually fragmented across source code, tests, product documents, design files, commit history, conversations, and human memory. Kraddle gives those pieces a shared structure that travels with the project.

01

What does it do?

Inputs, outputs, effects, states, and observed behavior.

02

What is it for?

The purpose, capability, or user outcome a unit serves.

03

What must it preserve?

Constraints, contracts, invariants, and experience qualities.

04

How does it relate?

Vertical realization and horizontal collaboration across the system.

Design principles

  1. Project-native.Meaning lives in .kraddle/ and travels with the project.
  2. Database-free.Canonical state, indexes, history, and synchronization are file-native.
  3. Local-first.Every operation works without a network connection.
  4. Evidence-backed.Observed facts, interpretations, and commitments remain distinct.
  5. Compact but recoverable.Normal storage is binary; readable export is always available.

CORE CONCEPTS

Meaning model

Meaning is composed from units, commitments, relationships, evidence, and scopes.

Meaning unitAnything Kraddle can discuss, from a product purpose to a function.
CommitmentWhat a unit does, is for, must preserve, or becomes in use.
RelationshipA typed semantic connection between two units.
EvidenceA source that supports, challenges, or explains meaning.
ScopeThe product, feature, revision, worktree, or alternative where meaning applies.

Meaning is compositional

product purpose
  └── realized_by → capability
        └── realized_by → behavior
              ├── implemented_by → UI component
              └── implemented_by → service
                    └── decomposed_into → function

CORE CONCEPTS

Truth and evidence

Kraddle never turns a plausible interpretation into an accepted truth silently.

observed

Directly present in code or runtime behavior. For user input, observation establishes that the statement was made, not that its content is true.

derived

Computed from observations using an explicit rule.

inferred

A plausible interpretation of available evidence.

accepted

Explicitly approved by an actor or trusted policy.

stale

May no longer describe the referenced revision.

!

Extractors write observations. Agents propose interpretations. Neither may silently create accepted commitments.

CORE CONCEPTS

Identity and scope

Meaning survives renamed files, refactored symbols, parallel worktrees, and alternative implementations.

Stable code anchors

repository identity
language
symbol kind
qualified name
signature fingerprint
structural fingerprint
source revision

After each scan, an anchor remap is marked exact, probable, ambiguous, or broken. Commitments never move across an ambiguous remap without confirmation.

Terminology map

The terms describe different kinds of abstraction. They are not competing names for the same thing.

KernelThe five physical primitives everything else is composed from.
VocabularyNamed kinds, modalities, relationships, states, and operations.
ProfileA validated arrangement of kernel records representing one recurring concept.
EnvelopeA profile whose job is to declare a context, resource, or authority boundary.

ARCHITECTURE / SPECIFICATION

Profile definition

A profile is not a new primitive. It is a validated arrangement of the five kernel records.

Profile instance
  = one root Unit
  + role-bearing Commitments
  + role-bearing Relationships
  + supporting Evidence
  + one or more Scopes

profile_id = root_unit_id
ProfileDefinitionVersioned schema for a profile's root kind, roles, fields, cardinalities, lifecycle, validation, and projections.
ownedCreated for the profile. History remains after profile deletion.
referencedExisting record linked by the profile. The profile cannot delete it.
sharedRecord may participate in multiple profiles, each with explicit scope.

Atomicity

Profile operations append one transaction containing all required kernel changes. Readers see the previous valid profile or the next valid profile, never a half-applied bundle.

create_profile → propose → accept → activate
                                      ↓
                              complete / supersede / invalidate / abort
i
Phase 0 target

ControlBinding, EvaluationProfile, and ExecutionEpisode are the first profiles required to prove the model.

ARCHITECTURE

Precision gradient

Meaning becomes only as formal as its risk and control needs require.

  1. R0

    Exploratory. Feeling, aspiration, or unresolved thought.

  2. R1

    Descriptive. Scoped human-readable statement.

  3. R2

    Structured. Typed conditions, effects, thresholds, and exceptions.

  4. R3

    Evaluatable. A protocol can return a qualified result.

  5. R4

    Executable. A test, analyzer, monitor, rule, or review procedure exists.

  6. R5

    Enforced. Failure gates, restricts, blocks, or escalates action.

Rigor is independent of truth, approval, satisfaction, freshness, and confidence.

ARCHITECTURE / ROADMAP

Remaining design work

Seven dependent specifications turn the current grammar into something implementable and falsifiable.

  1. 1. Profile metamodelDefine exact mappings, roles, cardinalities, validation, queries, and migrations.
  2. 2. Identity and atomicityMake multi-record profiles visible and synchronized as one valid transaction.
  3. 3. Typed invalidationSeparate epistemic, applicability, rationale, authority, realization, selector, and proxy dependencies.
  4. 4. Evaluation lifecycleSpecify satisfied, violated, unknown, indeterminate, and evaluation-failed semantics.
  5. 5. Response resolutionResolve what follows violation, unknown state, stale evidence, conflict, or failed evaluation.
  6. 6. Compilation lifecyclePreserve the chain from source meaning to activated guardrail and evidence.
  7. 7. Conformance suiteRun a deliberately adversarial closed-loop change and prevent silent control loss.

Completion template

Each design is complete only when it defines normative semantics, kernel realization, schema, lifecycle, operations, projections, and conformance tests.

FORMAT SPECIFICATION

Directory layout

One canonical `.kraddle/` workspace lives beside the code.

.kraddle/
├── manifest.krd       # identity and format version
├── schema.krd         # vocabulary and relationship types
├── heads.krd          # current causal event heads
├── events/            # immutable event segments
├── objects/           # content-addressed evidence
├── indexes/           # rebuildable file-native indexes
└── local/             # device state; never synchronized
✓
No database layer

No SQL engine, embedded database, graph database, or database service is part of local or cloud storage.

FORMAT SPECIFICATION

Binary encoding

KRD is a deterministic, framed binary container designed for compactness and forward compatibility.

!

Conceptual byte layout. KRD/KRI encoding is not implemented or verified. The semantic metamodel takes priority over binary optimization.

0–3Magic4B 52 44 00
4Majoruint8
5Minoruint8
6–7Flagsuint16
8–23Workspace IDid128
24–31Header lengthuint64

Frames are length-prefixed and checksummed. Readers can skip unknown optional frames without understanding them.

OPERATIONS

Extraction

Turn code, documents, tests, and runtime behavior into evidence-backed observations.

Discover→Parse→Analyze→Anchor→Observe→Confirm

OPERATIONS

Synchronization

Replicate immutable event frames and referenced objects without requiring a central service.

  1. Exchange heads.Compare causal event heads and format capabilities.
  2. Transfer gaps.Send missing frames and referenced content-addressed objects.
  3. Verify.Check event identities, causal parents, and checksums.
  4. Project.Update current views and rebuild affected index runs.

OPERATIONS

Closed control loop

Meaning governs one bounded act, evidence qualifies the result, and response closes or redirects the loop.

human intent
  → semantic model
  → accepted commitment
  → control binding
  → context and authority envelope
  → execution episode
  → observation
  → evaluation
  → response
  → invalidation and reevaluation
  → reconciled meaning and reality
satisfied

The declared evaluator established the commitment within its coverage boundary.

violated

Current evidence establishes a contradiction.

unknown

No current evaluation establishes a result.

indeterminate

Available evidence cannot support a decisive result.

evaluation_failed

The required evaluator could not complete correctly. This is never a pass.

REFERENCE

Format invariants

Rules every conforming Kraddle implementation must preserve.

  1. 01

    .kraddle/ is the canonical source of project meaning.

  2. 02

    Canonical and derived storage use no database engine or service.

  3. 03

    Inferred meaning never becomes accepted without an explicit actor or policy.

  4. 04

    Every observation names its source revision and extractor version.

  5. 05

    Conflicting accepted meaning is never silently discarded.

  6. 06

    Indexes are rebuildable and contain no unique meaning.

  7. 07

    Approval, evaluation, freshness, epistemic basis, rigor, and confidence remain independent.

  8. 08

    Every controlled execution declares scope, base revision, effects, and delegated authority.

  9. 09

    An actor cannot alter its governing controls without explicit delegated authority.

  10. 10

    Stale inputs invalidate dependent evaluations and context envelopes.

  11. 11

    Exceptions preserve rationale, authority, scope, compensating controls, and expiration.

  12. 12

    Completion requires evidence for every declared proof obligation.

  13. 13

    No result is called successful when a required evaluator failed or did not run.

  14. 14

    Every context completeness claim discloses omissions, unavailable sources, and blind spots.
